# 分集梗概 · 分批寫

骨架拍板之後才有這一步。給你：拍板後的骨架四塊 + 你負責的集數區間（比如第 11–20 集）+ 這個區間內落著的爽點。產出這些集的 `episodes` 條目。**只輸出 JSON 陣列，不要解釋、不要圍欄。**

## 每集三欄，缺一欄就是沒寫完

| 欄 | 寫什麼 |
| --- | --- |
| `synopsis` | 這一集發生了什麼。**敘述體**——出現 `「」“”` 引號對白就是在寫劇本，validate 會攔 |
| `hook` | 【鉤子】讓人點下一集的那個問題 |
| `suspense` | 【懸念】埋著沒解的線 |

## 硬規則

- 落在你區間裡的每個爽點（`beats[].episode`），對應那一集的梗概必須真的把 setup/payoff 演出來——爽點表說第 13 集打臉，第 13 集的梗概裡就得有打臉
- `sceneIds` / `characterIds` 只能用骨架裡登記過的 id
- 三人以上同框寫 `crowdPlan`（拆解方案：機位怎麼分、誰用背影和過肩帶過）。校驗按 `characterIds` 人數判，是代理指標——三人實際不同框的過場集，把事實寫成方案即可（「三人分處兩場，無同框，分場拍」），別空著
- 梗概裡出現雨、擁抱、人群、手部特寫這類生成難點，寫進 `warnings`（列舉：雨戲 / 肢體接觸 / 人群 / 手部特寫）。寧可多報
- 只寫你負責的區間，別越界補別人的集——合併時按 ep 排序拼接

## 批次大小

每批 ≤ 10 集。60 集一口氣寫，後半段一定崩——節奏塌、鉤子重複、人物漂移。批與批之間靠骨架和爽點表對齊，不靠上一批的原文。
